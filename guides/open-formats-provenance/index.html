Guide 28 · Computation

Open data formats and analysis provenance

Choose mzML, mzIdentML, and mzTab for their respective information layers, then preserve sample relationships, vocabulary meaning, and transformation history.

FOUNDATIONAL GUIDE · OCT 2026
ENZH
Before you begin: From raw data to reliable results

Make each result traceable to its evidence

An open format helps software exchange information. Provenance explains how a particular result was produced. Neither guarantees the other: a valid file can omit crucial context, and a detailed notebook can describe files that no longer match the analysis. Start from the processing layers in data analysis, then treat interchange, identity, and history as separate responsibilities.

The practical goal is specific: another analyst should be able to locate a reported result, find its supporting measurements, understand the sample relationships, and reconstruct the transformations. A file extension, database accession, or software name alone cannot provide that chain.

Choose a format for the information layer

  • mzML: represents mass-spectrometry spectra, chromatograms, and associated acquisition and processing metadata. It can contain profile or centroid data. It is not, by itself, a peptide-identification or concentration-results table. HUPO-PSI supplies the specification and validation resources. [1]
  • mzIdentML: represents peptide and protein identification evidence, including spectrum references, peptide sequences, modifications, scores, search information, and protein ambiguity. It references spectral data rather than replacing the underlying spectral files. Its core purpose is identification, not a general quantitative abundance matrix. [2]
  • mzTab: provides tab-delimited identification and quantification results with metadata. It is useful for exchanging accessible result summaries, while detailed evidence may live in linked resources. State the applicable version and domain rather than treating all mzTab variants as interchangeable. [3]
  • mzTab-M: specializes the tabular approach for metabolomics and lipidomics results. Its molecule-summary, feature, and evidence layers help preserve distinctions between a measured signal and an annotation. The released 2.0 specification is a defined reference here, not a claim about the newest available version. [4]

These formats complement each other. Exporting a final spreadsheet as mzML cannot reconstruct missing spectra; exporting identification results does not automatically preserve chromatographic integrations. Choose the information that must survive, then verify that the exporter actually carries it.

Preserve meaning as well as syntax

A controlled vocabulary assigns maintained identifiers and definitions to concepts. PSI-MS terms describe instruments, acquisition, processing, scores, and other MS concepts. Store the accession, applicable value and unit, and vocabulary version where supported. Human-readable names are useful, but matching a label alone is weaker than interpreting the defined term. [5]

Structural validation checks allowed file organization and data types. Semantic validation also checks appropriate terms, units, relationships, and required context. Neither proves the sample label or molecular assignment is scientifically correct. Constructed units example: a retention coordinate of 12 minutes equals 720 seconds. A parser that keeps the number 12 but drops the unit can create a 60-fold discrepancy despite reading a syntactically valid number.

Map samples to runs and channels explicitly

One sample can produce several files through fractionation or repeated acquisition. One multiplexed file can represent several samples through labeled channels. Filenames alone rarely encode the full design. SDRF-Proteomics records relationships between samples and data files, together with experimental factors and technical metadata. [6]

Constructed mapping example: 3 labeled samples analyzed in 2 fractions produce 2 MS files and 6 sample-to-file relationships, assuming every sample occurs in each fraction. This does not mean 6 biological replicates. Preserve sample identifiers, channels, fractions, technical repeats, and relevant biological replicate identifiers so later software does not mistake relationships for independent observations.

Describe transformations as a connected history

Provenance connects inputs, activities, outputs, and responsibility. The W3C PROV model offers a general vocabulary for such relationships; it is not an MS file format or a requirement to adopt one particular workflow engine. [7] A useful MS record can apply the same idea with a readable manifest and linked logs.

For each processing stage, preserve input identifiers and checksums, software version, exact parameters, reference-database or library release, model identity, relevant environment information, output identifiers, and quality-control decisions. Capture random seeds when applicable, while recognizing that a seed alone may not ensure identical results across software or hardware. Record manual edits and exclusions as transformations, retaining the preceding version.

A checksum supports checking byte identity; it does not establish biological truth or correct sample attribution. If a converter changes compression or metadata, the checksum can change even when the numerical arrays agree. Conversely, identical files can be interpreted differently under different parameters. State whether a comparison concerns bytes, numerical values, assignments, or downstream conclusions.

Test what survived conversion and export

Preserve vendor originals when available and use separate outputs for conversion. Tools such as ProteoWizard support data access and conversion, but the tool name alone does not specify filtering or representation. [8] Inspect scan counts, MS levels, polarity, time range and units, precursor isolation information, and representative arrays. Document intentional differences, including centroiding or dropped scans.

At the results layer, check that spectrum references resolve to the intended files and identifiers, peptide modifications retain their meaning, scores retain their type, and missing values remain distinct from zeros. After a round trip, compare selected records and totals, not merely whether both programs open the file. A successful validator is evidence of conformance within its checks, not proof of a lossless or scientifically correct workflow.

Deposit a connected, interpretable package

ProteomeXchange coordinates proteomics data sharing through its participating repositories. Its submission guidance distinguishes raw data, result files, and metadata, and describes how supported result formats can link identifications to spectra. Repository-specific requirements should be checked for the actual submission. [9]

Include the sample map, acquisition and analysis descriptions, original and derived data as appropriate, database versions, and scripts or parameter files needed to interpret the results. Cite the original dataset when reanalyzing it and identify the new outputs. A project accession locates a deposit; record the actual files and their versions or checksums for a reproducible analysis. Sharing also requires appropriate rights and consent for the material.

Check your understanding

Does mzML replace mzIdentML?

No. They primarily describe different layers: spectral measurements versus identification evidence. Preserve their links.

Does a valid mzTab file prove a reported concentration is accurate?

No. Format conformance does not establish calibration, recovery, interference control, or scientific validity.

What is the smallest useful provenance question?

For this result, which exact inputs and transformations produced it? If a link is missing, record the limitation instead of inventing the history.

References & further reading

  1. HUPO Proteomics Standards Initiative. mzML specification and documentation.

    Authoritative format specification and controlled-vocabulary resources.

  2. Vizcaíno et al. (2017). The mzIdentML Data Standard Version 1.2, Supporting Advances in Proteome Informatics. Molecular & Cellular Proteomics 16, 1275–1285.

    Standards paper supporting spectrum, peptide, database-sequence and protein-group evidence links. Version 1.2 is cited for these concepts, not asserted to be the newest release.

  3. HUPO-PSI. mzTab: Reporting MS-based Proteomics and Metabolomics Results.

    Official format overview with the mzTab 1.0 and mzTab-M 2.0 resources. Supports lightweight result exchange and links to detailed evidence; no claim that every mzTab variant is interchangeable.

  4. HUPO-PSI and MSI. mzTab-M 2.0 metabolomics results specification.

    Official released format specification. Sections 5.2 and 5.4 distinguish samples/assays/runs and missing-data encoding; sections 6.3–6.5 distinguish molecule summaries, features, and identification evidence. A format declaration does not verify biological independence or determine the missing-data mechanism.

  5. Mayer et al. (2013). The HUPO proteomics standards initiative—mass spectrometry controlled vocabulary. Database 2013, bat009.

    Original PSI-MS controlled-vocabulary publication. DOI: 10.1093/database/bat009. Supports semantic annotation and stable concept identifiers; conformance does not establish scientific truth.

  6. Dai et al. (2021). A proteomics sample metadata representation for multiomics integration and big data analysis. Nature Communications 12, 5854.

    Primary MAGE-TAB/SDRF-Proteomics standard describing sample-to-file relationships, multiplexing, fractions, and experimental factors. The packet’s 3-sample/2-fraction example is constructed.

  7. W3C (2013). PROV-DM: The PROV Data Model. W3C Recommendation, 30 April 2013.

    Official domain-independent provenance model of entities, activities, derivation, and responsibility. It is not an MS file format or a requirement to use a particular workflow engine.

  8. Kessner et al. (2008). ProteoWizard: open source software for rapid proteomics tools development. Bioinformatics 24, 2534–2536.

    Primary software publication. DOI: 10.1093/bioinformatics/btn323.

  9. ProteomeXchange Consortium (2019). Data Submission Guidelines, version 3.0.1, 13 October 2019.

    Official published guidance distinguishing raw data, result files, and metadata and explaining linked submissions. Cited for durable concepts, not asserted to supersede current repository-specific requirements.
